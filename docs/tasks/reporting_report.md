# Reporting implementation handoff

Scope completed in `src/crypto_carry/reporting.py`, `tests/unit/test_reporting.py`, and this file. No other project files were edited by this implementer. No commits or subagents were used.

## Public behavior

- `write_run(root, config, backtests, quality, data_kind, label="baseline", inputs=None)` creates an immutable `outputs/run_<24 hex>/` directory and returns its `Path`.
- Identity includes the full effective config, SHA-256 of actual checkout code, caller input hashes, sorted strategy/filter identities, explicit synthetic/historical kind, and label. Creation time is operational metadata only. Code hashing covers `src/**/*.py`, `pyproject.toml`, and `uv.lock`; output directories are excluded. Temporary output roots still hash the executing checkout.
- Reuse requires successful verification of every saved artifact and an identical result fingerprint. That fingerprint includes raw financial/event rows, final positions and prices, status/reasons, pair state, exposure durations, native reconciliation counts, and data-quality evidence. A collision with changed results fails visibly.
- `verify_run(run_dir)` returns `valid`, `status`, `run_id`, `checked_files`, and detailed `mismatches`. It checks output hashes, required artifacts, undeclared files, manifest/directory identity, and the manifest checksum sidecar. Invalid JSON, non-object JSON, and failed/partial builds return invalid results. Manifest paths are constrained to the run directory.
- `regenerate_report(run_dir)` renders solely from stored CSV/Parquet tables in a temporary staging directory. Matching bytes are reused without changing modification times. Modified report/figure bytes fail visibly; missing derived files can be restored only if regenerated bytes match the original manifest. Source table corruption is rejected.
- A failed build preserves its directory and writes `status="failed"`, `artifacts_complete=false`, failure details, and hashes of available partial outputs. It cannot subsequently be reused as a successful run.

## Evaluation and interpretation

The reporter delegates metrics, H1 targets/summaries, opportunity aggregation and regime comparison to `evaluation.py`. Shared H1/opportunity datasets are taken once from the conditional portfolio (or the sole supplied portfolio), avoiding duplicated economic strategies in statistical summaries.

H1/H2/H3 judgments are descriptive. Incomplete coverage suppresses full-sample judgments. H2 requires both conventional strategy identities, correct funding-filter flags, the same daily timestamp calendar, valid metrics and complete coverage. H3 also requires both reported regime coverages. Synthetic reports and every figure explicitly state that they validate the pipeline only, not historical academic results. Overlapping H1 horizons, no causal inference, undefined metrics, daily partial observations, mark versus execution prices, full-fill assumptions, USDT parity, zero risk-free rate, no ADL/book/taxes/exchange-insolvency model, and pending AUM/robustness analyses are explained.

Attribution uses realized and unrealized spot, realized and unrealized perpetuals, funding, negative ordinary fees, and negative liquidation fees. It reconciles to final equity minus initial capital within the configured ledger tolerance. Slippage is kept in a separate informational row/column and never subtracted again. The exact test fixture's attributed loss is `-0.5980025` USDT, equal to the actual ledger's equity change.

Execution summaries include order/fill counts, rejected signals, failed attempts, transitions into openings/rebalances/corrections, renewals, close requests, liquidations, blocked orders, turnover, native counts, and exposure/cash/cooldown seconds. Participation quantiles use each order's quantity divided by volume recorded at submission, including unfilled orders; unavailable denominators remain missing. Portfolio time invested is the engine's union of exposed intervals; per-asset unhedged/cooldown times are shown without fabricating a portfolio union from their sum.

Each individual run's robustness table contains the run's own baseline metrics and an explicit `scenario_evaluated=false` comparison flag. It does not invent a cost sweep. The cost figure says `Sin escenarios de costos evaluados`; the root-owned robustness module writes actual comparisons separately.

## Integration notes

- The reporting API trusts the caller's choice of `data_kind` and declared input hashes; root's CLI owns strict historical eligibility and canonical economic input identities.
- Hash verification detects corruption, not source authenticity or a deliberately rewritten manifest plus checksum. Reports state that boundary.
- Only report/figure files are regenerated. Updating source tables or materially changing rendering requires a new run/version; silent overwrites are rejected.
- Rendering uses float copies of persisted values. Saved monetary accounting remains exact decimal text.
- Actual historical results and executed robustness/AUM comparisons remain conditional on the root's data/rules validation and scenario execution. The reporter does not backfill those results.
